As the ecosystem matures, we are transitioning full execution client support to **op-reth** and moving from **op-program** to **cannon kona**.

## What this means

- **op-geth is supported through May 2026.** Security patches and critical bug fixes will continue to be issued during this window, after which support ends.
- **op-program is also reaching end-of-support.** The fault proof program is transitioning from **op-program** to **kona-cannon**.

## Action required

**The Glamsterdam hardfork will not support op-geth.** Chains still running op-geth at activation will not be able to follow the canonical chain.

All node and chain operators must migrate to op-reth before Glamsterdam activates. Do not wait for the hardfork to be scheduled—**start now**.

<Warning>
  op-geth reaches end-of-support in **May 2026**. Glamsterdam will break compatibility with op-geth. Begin migrating immediately.
</Warning>

### Migration

Start syncing an op-reth node alongside your existing op-geth node. Validate sync correctness over a meaningful window—compare block hashes, state roots, and RPC outputs. Once confident, migrate production traffic to op-reth.

As soon as op-reth is fully synced, take a chain snapshot and store it in durable off-node storage. This is your recovery safety net for the hardfork transition. Refresh it regularly as Glamsterdam approaches.

<Info>
  Syncing op-reth takes time. Start early to allow adequate validation before the hardfork window.
</Info>

## Proof system transition

In parallel, the fault proof program is moving from **op-program** to **kona-cannon**. Optimism will handle the onchain prestate updates for managed chains. If you operate a permissionless fault proof chain, watch for a separate notice with specific steps.

<Info>
  **kona-node is not required for cannon-kona.** You can run kona-cannon with your existing **op-node** setup. kona-node is a separate, optional component and is not part of the fault proof program migration.
</Info>
